هدف الجلسة

نتعاون دون الكتابة مباشرة على main: GitHub Flow، رفع الفرع، Pull Request، المراجعة، Issues، والفرق بين Fork والدعوة.

04

الشرح النظري

1) GitHub Flow

مسار العمل القياسي للفرق الصغيرة:

  1. حدّث main: git switch main ثم git pull.
  2. أنشئ فرع ميزة من main.
  3. اعمل commits صغيرة واضحة.
  4. ادفع الفرع إلى GitHub.
  5. افتح Pull Request.
  6. بعد المراجعة ادمج إلى main واحذف فرع الميزة إن انتهى.
تشبيه: لا ترمّم الشارع وأنت تغلقه على الجميع. ابنِ في الورشة (الفرع) ثم اطلب موافقة لفتحه على الشارع (PR).

2) رفع فرع بعيد

git switch -c feature/contact
# edit files, add, commit
git push -u origin feature/contact

بعدها يظهر الفرع في تبويب Branches على GitHub، ويقترح الموقع غالباً «Compare & pull request».

3) Pull Requests

طلب الدمج صفحة على GitHub تقارن فرعك بـ main (أو أي فرع هدف). العنوان يلخّص العمل، والوصف يشرح ماذا ولماذا وكيف الاختبار.

  • Open: بانتظار المراجعة أو الدمج.
  • Draft: عمل غير جاهز — لا يُدمج عادة.
  • Merged: دخل main.
  • Closed: أُلغي بلا دمج.

خيارات الدمج الشائعة: Merge commit يبقي كل التاريخ، Squash يلخّص فرعك في commit واحد (مناسب للدورة)، Rebase يعيد ترتيب اللقطات — لاحقاً بعد إتقان الأساسيات.

4) المراجعة والدمج

المراجع يقرأ الفرق (Files changed)، يضع تعليقاً على سطر، ويوافق أو يطلب تعديلات. صاحب الفرع يدفع commits جديدة على نفس الفرع فتظهر في نفس الـ PR تلقائياً.

لا تدفع إلى main مباشرة في عمل جماعي. حتى وأنت وحدك، الـ PR يدرّبك على وصف التغيير قبل دمجه.

5) Issues

المسألة تذكرة عمل: خطأ، فكرة، مهمة. العنوان واضح، والجسم خطوات إعادة الخطأ أو قبول المهمة. يمكن ربطها في الـ PR بكتابة Closes #12 فتُغلق عند الدمج.

التصنيفات (Labels) مثل bug و enhancement تساعد على الفرز. Assignees تحدد المسؤول.

6) Fork مقابل Collaborators

Collaborators

صاحب المستودع يدعوك من Settings → Collaborators. تدفع فروعاً إلى نفس المستودع ثم تفتح PR داخلياً. مناسب لفريق الدورة.

Fork

نسخة تحت حسابك من مشروع شخص آخر (شائع في المصادر المفتوحة). تدفع إلى الـ fork ثم تفتح PR نحو المستودع الأصلي.

7) وصف الـ PR الجيد

  • ماذا تغيّر في جملة.
  • لقطات شاشة إن كان التغيير مرئياً.
  • كيفية التجربة محلياً.
  • ربط الـ Issue إن وُجد.

نجوم المستودع وWatch للإشعارات مفيدة للمتابعة، لكنها ليست بديلاً عن الـ PR. Discussions وWiki موجودة في GitHub؛ نكتفي بمعرفتها دون التعمّق في هذه الجلسة.

أمثلة عملية

مثال 1: فرع ثم دفع

git switch main
git pull
git switch -c feature/contact
echo "<h1>Contact Osama Bittar</h1>" > contact.html
git add contact.html
git commit -m "Add contact page"
git push -u origin feature/contact

مثال 2: نص وصف PR

Title: Add contact page

This pull request adds a simple contact heading
for the academy site of Osama Bittar.

Closes #3

مثال 3: تحديث نفس الـ PR بعد ملاحظة

echo "<p>Email coming soon.</p>" >> contact.html
git add contact.html
git commit -m "Clarify contact page copy"
git push

لأن الفرع يتتبع origin/feature/contact يكفي push بلا -u مرة ثانية.

مثال 4: بعد الدمج محلياً

git switch main
git pull
git branch -d feature/contact

احذف الفرع البعيد من GitHub عبر الواجهة أو بعد التأكد أن الـ PR مدمج.

تمارين عملية

1 Issue

أنشئ Issue بعنوان Add pricing note ونص يوضح أن السعر باليورو.

GitHub → Issues → New issue → العنوان والوصف → Submit. انسخ الرقم مثل #4 لربطه لاحقاً.

2 PR من فرع

ادفع فرعاً يضيف سطراً في notes.txt وافتح Pull Request يدمج إلى main.

git switch -c feature/note
echo "GitHub flow practice" >> notes.txt
git add notes.txt
git commit -m "Add GitHub flow practice note"
git push -u origin feature/note

ثم Compare & pull request على GitHub.

3 ربط الإغلاق

في وصف الـ PR اكتب Closes ورقم الـ Issue.

Closes #4

ملخص الجلسة

  • GitHub Flow: فرع → commits → push → PR → مراجعة → دمج
  • Issues تتبّع العمل وتُغلق من الـ PR
  • الدعوة للتعاون داخل المستودع · الـ Fork للمشاريع الخارجية
  • لا تعتمد على الدفع المباشر إلى main في الفريق

واجب الجلسة

  • Issue واحد + فرع + Pull Request مدمج إلى main
  • وصف الـ PR يذكر اسم Osama Bittar في سياق الأكاديمية
  • أرسل روابط الـ Issue والـ PR
